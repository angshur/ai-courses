Five Patterns Behind Every AI Agent System

Stop thinking by pattern name. Start thinking by the job each pattern performs.

By Angshuman Rudra

The Core Idea

Every agent system—from coding agents to research agents to enterprise AI—is doing five jobs.

LangGraph, OpenAI Agents, CrewAI, AutoGen, Manus. The names change. The jobs don't.

When you understand the five jobs, you can read any agent architecture and understand it in minutes.

Category 1 of 5

Decomposition & Planning

Breaking large goals into pieces that agents can actually execute.

Question it answers: What work needs to be done?

Category 1 — Decomposition / Planning

Three Planning Patterns

Pattern 1.1

Planner → Executor

Goal ↓ Planner ↓ Tasks ↓ Executor(s)

One agent plans, separate agents execute. The planner never touches the work directly.

"Analyze my marketing performance" → planner creates 4 tasks → executors do the work.

Pattern 1.2

Hierarchical Planning

CEO Agent ↓ Manager Agent ↓ Worker Agents

Large objectives become sub-goals, which become tasks. Multiple levels of planning authority.

Very common in research systems and long-horizon agents.

Pattern 1.3

Recursive Decomposition

Goal ↓ Subgoal ↓ Sub-subgoal ↓ Executable Work

Keep breaking until each unit is small enough to execute reliably in one step.

Category 2 of 5

Execution

Actually getting the work done — thinking, acting, observing, repeating.

Question it answers: How do we do the work?

Category 2 — Execution · Pattern 2.1

The ReAct Pattern

Probably the most influential pattern in modern AI agents

Think
↓
Act
↓
Observe
↓
Think
↓
Act

The agent reasons about what to do, takes an action, observes the result, then reasons again. It loops until the task is done.

Most modern agents — Claude Code, coding agents, research agents — are ReAct variants.

Example
Think: I need the weather in Tokyo. Act: call weather API Observe: {"temp": 22, "condition": "cloudy"} Think: I have the data I need. Act: answer user

Category 2 — Execution

Two More Execution Patterns

Pattern 2.2

Tool-Using Agent

Reason ↓ Choose Tool ↓ Execute ↓ Continue

The agent selects from a menu of tools and invokes them as needed. A specialization of ReAct where the actions are pre-defined tool calls.

Common tools: web search, SQL, Slack, Salesforce, Python executor, file system, APIs

Pattern 2.3

Workflow / Chain

Step A ↓ Step B ↓ Step C ↓ Output

Deterministic, pre-defined pipelines. Each step's output is the next step's input. No dynamic reasoning about what to do next.

Common in enterprise AI where auditability and predictability matter more than flexibility.

Category 3 of 5

Coordination & Routing

Deciding which agent handles which request — and how multiple agents collaborate.

Question it answers: Who should do the work?

Category 3 — Coordination / Routing

Three Coordination Patterns

Pattern 3.1

Router Pattern

Request ↓ Router ↓ Agent A / B / C

An agent or classifier reads the request and sends it to the right specialist.

Analytics Agent · SEO Agent · Finance Agent. The router decides who gets the ball.

Pattern 3.2

Specialist Pattern

General Agent ↓ Specialist Agent

A generalist agent hands off to a specialist with deeper expertise in a narrow domain.

SQL Expert · Data Scientist · Copywriter. The generalist knows when to defer.

Pattern 3.3

Swarm Pattern

Task ↓ Agent 1 Agent 2 Agent 3 ↓ Combined Result

Many agents work in parallel on the same task. Results are aggregated.

Useful for broad research, parallel code generation, covering many sources simultaneously.

Category 4 of 5

Evaluation & Quality Control

Deciding if the work is actually good — before it ships.

Question it answers: Is the work good enough?

Category 4 — Evaluation / Quality Control

Two Core Evaluation Patterns

Pattern 4.1

Generator → Reviewer

Generate ↓ Review ↓ Improve

A separate reviewer agent critiques the generator's output. The generator revises based on feedback.

The most widely used quality pattern. Separation of concerns: one agent creates, another judges. Neither role bleeds into the other.

Pattern 4.2

Reflection

Generate ↓ Reflect ↓ Revise

The same agent reviews its own output before delivering it. No separate reviewer.

Simpler to implement. Less effective than a separate reviewer — self-critique has limits. Best when an external reviewer isn't practical.

Category 4 — Evaluation / Quality Control

Three Advanced Evaluation Patterns

Pattern 4.3

Debate

Agent A Agent B ↓ Judge

Two agents argue opposing positions. A judge evaluates and picks the stronger argument.

Useful for decisions with real tradeoffs — forces surfacing of both sides.

Pattern 4.4

Judge Pattern

Candidate A Candidate B Candidate C ↓ Judge

Multiple agents produce independent outputs. A judge selects the best result.

Good when you want parallel diversity — let multiple agents attempt the task, pick the winner.

Pattern 4.5

Consensus

Multiple Agents ↓ Voting ↓ Answer

Multiple agents vote on an answer. Majority or weighted agreement determines the result.

Useful when correctness matters and you can afford to run the same task multiple times.

Category 5 of 5

Memory & Context Management

Deciding what to remember, what to retrieve, and what to forget.

Question it answers: What should we remember?

Category 5 — Memory / Context Management

Three Memory Patterns

Pattern 5.1

Short-Term Working Memory

Current Task ↓ Scratchpad

Temporary memory during execution — notes, intermediate results, reasoning steps.

Lives in the context window. Gone when the session ends. The agent thinks on paper.

Pattern 5.2

Long-Term Memory

Past Sessions ↓ Memory Store ↓ Future Tasks

Persistent storage of user preferences, past decisions, and accumulated knowledge.

What makes an agent feel like it "knows you." Survives session resets.

Pattern 5.3

RAG

Question ↓ Retrieve Context ↓ Answer

Retrieval-Augmented Generation. The agent fetches relevant documents before answering.

Still the most commonly deployed memory pattern in production systems.

Category 5 — Memory · The Emerging Pattern

Context Engineering

Pattern 5.4

Context Engineering

Many Sources ↓ Context Builder ↓ Agent

Instead of focusing on prompts, focus on context: what information is needed, which is relevant, how it should be compressed, what should be forgotten.

The four questions

  • → What information is needed?
  • → Which information is relevant?
  • → How should it be compressed?
  • → What should be forgotten?

Many practitioners now see context engineering as more important than prompt engineering. The model is a given. What you put in front of it is the craft.
